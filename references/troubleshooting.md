# 故障排查手册

按「现象 → 根因 → 处置」组织。处置命令均为 `macctl` 子命令（`M=~/.workbuddy/skills/mac-control/scripts/macctl`）。

---

## 0. 先跑这个（30 秒省掉十几轮排查）

```bash
M doctor
```

**任何「点了没反应」的问题，第一步都该是这条命令，而不是猜坐标。**

## 0.5 屏幕锁了：输入事件被静默丢弃 ⭐️ 最贵的坑

**现象**：点击不生效、粘贴不进字、`AXPress` 返回 success、`type` 报成功，
但界面**毫无变化**，而且**任何工具都不报错**。

**根因**：屏幕锁定时，macOS **静默丢弃所有 CGEvent 合成输入事件**。

**为什么容易漏**：`CGSSessionScreenIsLocked` 这个标志位**不会置位**，靠它判断会完全漏掉。

**唯一可靠的判据：实测移动光标，看位置是否真变。** `doctor` 就是这么做的。

| 候选信号 | 能否作判据 | 实测结果 |
|---|---|---|
| **移动光标后位置是否真变** | ✅ **唯一可靠** | 直接反映系统是否接受合成事件 |
| `CGSSessionScreenIsLocked` | ❌ | Swift 直读返回 **nil**；`ioreg` 里也读不到 |
| `pgrep -x loginwindow` | ❌ | **常驻登录进程**，解锁后依然在跑（pid=388 全程不变） |

> **D-013 血泪**：我曾用「`loginwindow` 存在」当判据，导致**屏幕明明解锁却报「已锁定」**，
> 所有需要输入的脚本全部拒绝执行。
> 更隐蔽的是——因为先判 `locked=true`，代码里 `if !locked { 做输入自检 }` 被跳过，
> **唯一的可靠证据被自己的误判屏蔽了**。
>
> **教训**：不要相信任何单一信号。防御方式是用实测交叉验证；
> 更根本的是——**上游脚本要对工具结论保持怀疑，而不是无条件采信**。

**识别**：
```bash
M doctor
#=== 闪控环境体检 ===
# 屏幕锁定: 否
# 输入通道: ✅ 正常
```

**处置**：解锁屏幕。不需要重启任何东西。

**代价对比**：不预检的话，一次「点击无效」的排查要花掉十几轮坐标猜测、AX 树检查、
锁屏标志位检查、应用状态检查、VIP 限制检查、高层浮窗检查……而根因只是「用户不在电脑前，
屏幕自动锁了」。

> 建议：**把 `doctor` 放在所有需要模拟输入的操作之前**，作为固定前置步骤。

## 0.6 自绘控件：AX 拿不到焦点

**现象**：AX 树完全正常、`find --text "搜索"` 精准命中坐标、点下去也确实有反应，
但 `type` 之后 value 恒为空。

**决定性诊断**：
```bash
M clear --app <id>
# 输出「清空输入框 [quartz]」
```

`[ax]` = AX 路径成功，控件存在。
**`[quartz]` = AX 路径失败、退化到 Quartz 合成事件 —— 说明没有任何输入控件持有焦点。**

**根因**：该控件是应用**自绘**的（自己画 UI，只向 AX 暴露一个占位元素）。AX 能看见它，点得动它，但无法给它输入焦点。

**已知实例**：微信 4.x macOS 版顶部搜索框。

**处置**：这是**应用侧限制**，任何坐标技巧或按键序列都绕不过去。可行路径只有：
1. 改走其他入口（会话列表逐项匹配、新建聊天入口、URL Scheme）
2. 让用户手动打开目标会话，脚本跳过搜索直接操作

> **不要在这个控件上继续尝试坐标或按键技巧**——会浪费大量轮次且不可能成功。

## 1. AX 树返回 0 节点 / 窗口列表为空

**这是第二高频故障，且极易被误判为权限问题。**

### 根因 A：目标窗口被完全遮挡
macOS 对被遮挡的应用**停止 AX 投递**，AX 树直接变空。

**识别**：
```bash
M diagnose --app <bundleId>
```
输出会列出所有遮挡者（WorkBuddy 自己、千问、微信、系统设置……）。

**处置**：
```bash
M raise --app <bundleId>      # 自动寻找目标窗口上未被遮挡的点并点击
M winback --app <bundleId>    # 把非主窗口移出屏幕再移回，强制退到窗口序后面
M dock --app "应用名"          # 点 Dock 图标切换，最可靠
```

### 根因 B：应用自己收起了主窗口
某些 app 在特定页面（如酷狗搜索结果展开）会把主窗口从窗口列表移除，只留辅助窗。

**识别**：`M scwindows --app <bundleId>` 里主窗口消失，但 AX 仍有少量节点。

**处置**：点 Dock 切走再切回，通常能恢复。

### 根因 C：模态对话框阻塞
`M axwindows --app <bundleId>` 会显示每个 AX 窗口的节点数，若某窗口 0 节点而其他正常，即为模态阻塞。

**处置**：`M close-popup --app <bundleId>`（发 ESC）。

### 根因 D：解析层失败被误读成「元素不存在」⚠️ 隐蔽
工具层（解析器/查表）出问题时，如果**静默返回空值**，上层会把它读成「树是空的」。

**识别**：落盘文件明明有内容（`wc -c` 正常），但解析结果为空。
检查解析器是否对**未知函数名**报错退出（`parsers.py` 应对未知名字 `exit 3` 并列出可用名单）。

**处置**：让工具层**显式报错**，不要静默兜底。静默兜底会让「工具故障」被误读成「业务对象不存在」，
把排查方向完全带偏。

## 2. 元素找到了但点不动

### AXPress 是 no-op
Electron 系 app（微信、酷狗、VS Code 类）常见：`AXUIElementPerformAction` 返回 `.success` 但界面无变化。

**macctl 已内建降级**：`click` 先试 AXPress，随后用 `signature()`（窗口标题+位置、焦点、节点数）检测界面是否变化，无变化则改用 Quartz 真实鼠标事件。

**手动处置**：改用 `M click --at x,y`。

### 文本类元素要点在偏左位置
`AXStaticText` 的 AXPosition 是整行起点，文字只占左侧几十像素。
`macctl click` 对 `AXStaticText`/`AXTextArea` 会自动点 `pos.x + min(24, width/2)`，避免点到空白处。

## 3. 中文输入失败

### Unicode 注入吐出乱码（如 "aa"）
某些 app 的输入框不响应 `CGEvent.keyboardSetUnicodeString`。

**处置**：用剪贴板粘贴。`macctl type` 会按 `ax → paste → unicode` 顺序尝试，**首次成功后自动记住**该 app 的有效方式，写入 `~/.workbuddy/skills/mac-control/cache/learned.json`。

```bash
M recall              # 查看已记住的方式
M note --app <id> --text "备注"   # 补充交互模型
```

### 粘贴后没反应
粘贴目标不对。检查焦点：
```bash
M state --app <id>    # 看「焦点」段
M click --text "输入框文字" --app <id>   # 先点中目标
```

## 4. 截图 / 坐标对不上

### 裁剪区域与实际内容不符
**根因**：SCK 捕获图像的行序为**自上而下**，与屏幕坐标同向。若按 CGImage 的左下原点习惯去翻转 Y，会裁到错误区域。

`macctl` 的 `crop` 已按屏幕坐标同向处理，直接用即可。

### Retina 缩放
截图像素是屏幕逻辑点的 2 倍。`scan` 输出的裁剪图上量出的像素 ÷ 2 = 屏幕逻辑点。

`scan` 输出会明确给出「屏幕坐标基准」，照着换算。

### 截图里是别的 app
目标窗口被遮挡时，屏幕截图拍到的是上层窗口。此时应：
- 用 `M raise` / `M dock` 置前目标 app；或
- 用 SCK 排他捕获（`exceptingWindows`）拍目标窗口内容——`macctl` 的 `shot --app` 已支持。

## 5. 音量相关

### 区分系统音量与应用内音量
- **系统输出音量**：`M volume --set 70`（用 AppleScript，无需 AX）
- **应用内音量**：优先 `M app-volume --app <id> --to N`（找 `AXSlider`）
- 若 app 用自绘滑条：`M set-volume-bubble --app <id> --to N`（像素几何 + 读回闭环）

### 音量气泡是瞬时的
点击喇叭后气泡只存在很短时间，脚本里若先 `sleep` 再读就读不到了。
`M vol-probe` 是原子化的：点击后立即连读。

### 气泡点击会误触
音量气泡常是**开关式**——多点一次反而关闭。`set-volume-bubble` 会先检测气泡是否已存在，存在则不重复点击。

## 6. 性能

| 症状 | 原因 | 处置 |
|---|---|---|
| `state` 慢 | depth 过大，遍历节点多 | 用 `--depth 6`；只在需要时用 `--depth 40` |
| `overview` 输出太长 | 190 个窗口 | 用 `grep` 过滤；`overview` 只看 app 聚合段 |
| AX 树为空时反复试 | 见第 1 条 | 一次 `diagnose` 定位根因，不要循环试 |
| 脚本总耗时远超预期 | 累加了大量固定 `sleep` | **改用条件等待**（见下） |

### 不要用 `sleep`，用条件等待

「`sleep 2` 然后 `find`」把等待时间全花在盲等上。正确做法是「条件一成立就返回」：

```bash
# ❌ 慢：无论界面多久更新，都固定等 2 秒
sleep 2; M find --text "播放" --app <id>

# ✅ 快：立即就绪约 400ms，超时上限由 --timeout 控制
M probe --app <id> --text "播放" --timeout 5
```

**实测差距（超时场景）**：shell 轮询 13.4s vs `probe` 5.5s —— 快一个数量级。
`probe` 在 Swift 进程内完成「拿树 → 判定 → 等 → 再判定」，没有反复启动进程的固定开销。

重试间隔按 `min(0.6, 0.2 × 1.6^n)` 递增：起手快、后段慢，兼顾响应速度与不空转。

### 两个常见的「超时了却等了很久」

| 症状 | 根因 | 修正 |
|---|---|---|
| `timeout 3` 实际跑了 13s | 步进换算 `int(gap*10)` 把 0.25 截成 0.2，每轮少算 0.05s，累积后严重超时 | 用**毫秒整数累加**，只在开头调一次运行时 |
| 明明立即就绪却等满全程 | 判据在动作发生**之前就已成立** → 立即返回是对的，但上层用的是另一个错误判据 | 换用「目标元素真的出现」作判据（如「歌名命中数 ≥ 2」区分联想浮层与结果页） |

## 7. 权限相关

| 现象 | 检查 |
|---|---|
| `state` 报 0 节点且 `diagnose` 显示无遮挡 | Accessibility 权限 → 见 `permissions.md` |
| 截图全黑 / 只有壁纸 | ScreenCapture 权限 |
| 真实点击无效（AXPress 有效） | Input Monitoring 权限 |
| `osascript` 报权限违例 (-10004) | Automation 权限 |

## 8. 事件注入失效的排查顺序

1. `M state --app <id>` 看焦点是否在预期控件
2. `M click --at x,y` 手动点一下，看界面是否有反应（区分「点不到」和「点到了但没触发」）
3. 检查目标 app 是否在**当前鼠标位置之外**——Quartz 事件是全局的，与前台无关
4. 确认 `CGEventSource(stateID: .hidSystemState)` 未被系统拦截
